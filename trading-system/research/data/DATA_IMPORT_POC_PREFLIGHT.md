## 2. 退避・削除が必要なファイル（**方針のみ。実ファイル名は§1確定後**）

理由: 外部M1だけをImportし、既存のRakuten由来 M5/M15/M30/H1 が残ると、
**同一シンボル内でData Sourceが混在**する。Strategy TesterはM1から上位足を再構築するとは限らず、
既存の上位足`.hst`を参照しうるため、「M1 = HistData / H1 = Rakuten」という状態が起こりうる。
これはunmatched chart errorsやTester結果差の原因になり、DIAG-DATA-001（source sensitivity）の
測定対象を汚染する。

方針:

| 対象 | 扱い | 理由 |
|---|---|---|
| POC環境 `history\<server>\USDJPY*.hst`（全時間足） | **退避（リネーム or 別フォルダへ移動）**。削除はしない | Import後にHistData由来へ完全置換するため。復元可能性を残す |
| POC環境 `tester\history\USDJPY*.fxt`（USDJPYのみ） | **削除** | Tester cacheは再生成される派生物。他通貨ペアのcacheは対象外 |
| 現行Rakuten研究環境（LEGACY_DATA_EPOCH生成環境）の全ファイル | **一切触れない** | ユーザー指示。既存Evidenceの再現性を保持 |

退避先の例（POC環境内）: `history\_backup_rakuten_YYYYMMDD\` を作り、そこへ移動。
`.fxt`は再生成可能だが、不安なら同様に退避でもよい（動作上はどちらでも可）。

**実際の削除・退避は§1の一覧を受け取り、対象ファイルを個別に列挙して合意してから行う。**

## 6. インポート順序

1. POC環境のMT4を**起動したまま**にせず、まず一度終了する（`.hst`はメモリ上にキャッシュされるため）
2. §2に従い、POC環境の `history\<server>\USDJPY*.hst` を退避、`tester\history\USDJPY*.fxt` を削除
3. MT4を起動する。**この時サーバーから自動再取得されないよう、可能ならオフラインで起動する**
   （回線遮断、またはツール→オプション→チャート→「ヒストリー内の最大バー数」を絞る等）
4. ツール → ヒストリーセンター → USDJPY を選択
5. **M1 から順に**インポート: M1 → M5 → M15 → M30 → H1
   - 各時間足を選択 → インポート → ファイル指定 → 区切り文字「,」→ OK
   - 「選択したものを使用」チェックは外す（全行取り込み）
6. すべてImport後、ヒストリーセンターを閉じてMT4を再起動（`.hst`をディスクへ確定させる）

M1を先に入れる理由: MT4は下位足から上位足を補完生成することがあるため、
先に上位足を入れると後続のM1 Importで上書き・再生成が起こり、どの足がどのソース由来か
判別できなくなる。M1を基準に置き、その後に明示的に上位足を上書きする。

## 7. Tester cache（`.fxt`）再生成手順

- `.fxt` は `.hst` から生成される派生ファイル。**§2で削除済みなので、次回Strategy Tester実行時に
  自動再生成される**
- 再生成のトリガー: Strategy Tester でUSDJPY/H1を選択し、任意の期間で1回実行する
- 再生成後、`tester\history\USDJPY60_*.fxt` の**更新日時が今日**になっていることを確認する
- 削除対象は**USDJPYの`.fxt`のみ**。他通貨ペアの`.fxt`は一括削除しない
- **この操作は分離POC環境でのみ行う。現行Rakuten研究環境の`tester\history\`には触れない**

## 9. 由来の同一性検証（M1/M5/M15/M30/H1）

「すべて同一HistData + 同一OFFSET_SCHEDULE由来」を、宣言ではなく機械的に検証した。

### 9-1. 単一プロセスでの生成

5本すべてを**1回のスクリプト実行**で生成した。M1ソースの読み込みは1回、
`OFFSET_SCHEDULE`の適用も1回で、その結果の`shifted`辞書から各時間足を集約している
（`histdata_to_mt4.py::main`）。時間足ごとに別ソース・別オフセットを与える経路は存在しない。

入力: `DAT_ASCII_USDJPY_M1_{202508,202509,202510}.csv`（3ファイルのみ）
適用オフセット: `[(1970-01-01, +7), (2025-10-25, +8)]`

### 9-2. 出力M1からの再導出テスト

より強い検証として、**生成済み`USDJPY_M1_MT4import.csv`だけを読み直し**、
そこからM5/M15/M30/H1を再集約して既存の出力ファイルと**行単位で全比較**した。

## 10. MT4 Import設定（全CSV共通）

ファイル形式はすべて同一なので、5本とも同じ設定を使う。

| 項目 | 値 | 理由 |
|---|---|---|
| Symbol | USDJPY | POC環境のシンボル名と一致させる（`USDJPYm`等の接尾辞が付く業者の場合はそちらを選ぶ） |
| Period | ファイル名の時間足と一致させる | M1のCSVはM1へ、H1のCSVはH1へ。**ここを間違えると足種が混線する** |
| 区切り文字 (Separator) | `,` (Comma) | 出力形式がカンマ区切り |
| Skip columns | 0 | 先頭列から `Date,Time,O,H,L,C,V` の順で並んでいる |
| Skip rows | 0 | **ヘッダー行なし**。1行目から実データ |
| Use selected only | **チェックしない** | 全行を取り込む |
| Shift (時刻シフト) | **0** | オフセットは変換側で適用済み。MT4側で二重にずらさない |

### 10-1. Import前に必ず設定するもの

ツール → オプション → チャート:
- **「ヒストリー内の最大バー数」= `99999999`**
- **「チャートの最大バー数」= `99999999`**

既定値（例: 65000）のままだと、Import時に古いバーが黙って切り捨てられる。
本POCは94,217本のM1を入れるため、この設定を先にしないとM1が欠ける。

### 10-2. 自動ダウンロードによる汚染リスク（POC環境が空であることに起因する新規リスク）

POC環境にはUSDJPY履歴が1件も無い。これは削除作業が不要という利点がある一方、
**MT4がサーバー接続時に自動でヒストリーを取得しに行く**ため、次の順序を守らないと
Rakuten由来データがHistData由来データに混入する。

1. Import**前**に、USDJPYのチャートを開かない（開くと自動ダウンロードが走る）
2. Import**後**は、Strategy Tester実行までUSDJPYチャートを開かない
3. 可能であれば、Import後はオフライン（ログアウトまたは回線遮断）でTesterを実行する

なお、シンボル仕様（契約サイズ・ティック値・桁数）はサーバー接続時に取得されるため、
**一度もサーバーへ接続していない場合、ヒストリーセンターにUSDJPYが出てこない可能性がある**。
その場合は「一度だけ接続してシンボルを認識させ、チャートは開かずに切断してからImport」する。
ヒストリーセンターにUSDJPYが表示されるかどうかを、手順の最初に確認する。
