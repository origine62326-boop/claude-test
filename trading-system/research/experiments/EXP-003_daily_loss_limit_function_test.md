`EXPERIMENT_TEMPLATE.md`に基づく実験記録。**本ファイルは実際のバックテストデータを見る前の事前登録である。
`MaxDailyLossPercent`の具体値は本ファイル内で確定せず、下記「候補値と根拠」を提示した上でユーザー承認を
待つ。承認された値が確定するまで`status = DRAFT`のまま維持し、`READY`へは進めない。**

## この実験の性質（重要）

**本実験は収益性評価には使用しない。** PF・純利益・勝率等の取引成績は測定しても採用可否の判断材料としない。
目的はただ一つ、「`MaxDailyLossPercent`による新規エントリー停止・日付変更時のリセット・翌日の正常再開が、
コードの意図通りに動作するか」という**機能そのものの実動作確認**である（`EXP-002`のExpertsログ解析で、
連敗制限機能はVERIFIEDと確認できた一方、日次損失上限機能は本バックテスト期間中に一度も到達せず
NOT_TRIGGEREDのまま残っていたことへの対応、`EXP-002`「Expertsログ解析結果の反映」節参照）。

## 候補値と根拠（要ユーザー承認、本ファイルでは確定しない）

`DS004`（`EXP-002`使用データ、既存の実トレード196件）から、決済時刻ベースで日次損益を再集計し、
各日の始値時点残高に対する損失率を算出した（`reports/normalized/EXP-002_run001_trades.json`の
`profit`と`close_time`を使用。EA実装の`GetTodayRealizedNet()`と同様に、決済時刻の属する暦日ごとに
実現損益を合算する方式）。**この試算は決済済みトレードの実現損益のみを集計したものであり、EA実装が
判定に含める含み損部分(`GetFloatingLossOnly()`)は含んでいない。含み損を含めると実際の到達タイミングは
本試算よりわずかに早まる可能性がある。**

| 日次損失率のしきい値X | 本データで到達したと推定される日数 |
|---|---|
| 0.10% | 91日 |
| 0.15% | 78日 |
| 0.20% | 52日 |
| 0.25% | 24日 |
| 0.30% | 14日 |
| 0.40% | 4日 |
| 0.50% | 1日（2025-09-09、-0.5482%が本データ中の最悪日） |
| 0.75%以上 | 0日 |

参考: 実際に連敗制限が発動した2026-05-14は日次実現損益-0.3300%、2026-06-17は-0.2708%だった
（いずれも3連敗が同一日に収まったケース）。

以下3案を候補として提示する。いずれも「本試算通りに再現される保証はない」点に注意（新規エントリーが
一度でも止まれば、その後の値動きへの追従経路がEXP-002とは変わり、以降のトレード自体が変化しうるため。
これはEXP-002で観察された「取引数+12件・要因未特定」と同種の効果であり、本試算は「変化がないと仮定した
場合の目安」に過ぎない）。

| 案 | `MaxDailyLossPercent` | 推定発動日数(目安) | 想定されるメリット・デメリット |
|---|---|---|---|
| A（保守的） | 0.5 | 1日程度 | 最悪でも1回は発動する見込みだが、発動回数が少なく「日付変更後の解除」等の再現性を複数回確認しづらい |
| B（中庸、**推奨**） | 0.3 | 14日程度 | 複数回の発動・再開サイクルを確認でき、評価項目1〜6の再現性チェックに十分な回数が見込める。閾値が本来の既定値(2.0)から見て不自然に低すぎない範囲でもある |
| C（積極的） | 0.2 | 52日程度 | 最も多くの発動事例が見込め統計的に手厚いが、取引の半分近い日で新規エントリー停止が絡むため、EXP-002からの経路乖離（取引数増減等）が大きくなりやすく、機能確認以外のノイズが増える可能性がある |

**現時点ではB案（0.3%）を推奨するが、最終的な値の決定はユーザーに委ねる。承認された値を本ファイルの
本節に追記し、`status`を`READY`へ進める。**

## 評価項目（事前登録、結果を見た後に変更しない）

1. 日次損失制限が1回以上発動する
2. 発動日時をログで特定できる
3. 発動後、その日は新規注文がない
4. 日付変更時に基準残高(`DailyRiskReferenceBalance`)が再設定される
5. 翌日に有効シグナルがあれば正常に再開する
6. 既存ポジションの扱いが仕様通りである（`RISK_ENGINE_SPEC.md`記載の「既存ポジションの管理には影響しない」設計通りか）
7. エラー、無限ループ、注文異常がない

## acceptance_criteria / rejection_criteria

- 評価項目1〜7すべてがYESであれば、日次損失上限機能を`VERIFIED`とする（`EXP-002`の連敗制限機能と
  同じ扱い）。この時点で初めて、H002全体（連敗制限+日次損失上限の両方）についてPrimary/Secondary/
  Guardrail Metricsに基づく最終判定（ADOPTED/HOLD/REJECTED、`EXP-002`参照）を検討できる
- いずれか1項目でもNOであれば、`REJECTED`ではなく`HOLD`とし、原因調査を優先する（実装バグかテスト
  設計の不備かを切り分ける。`RESEARCH_RULES.md`第3節の精神に基づき、結果を見た後に閾値を変更して
  再実行する場合は本ファイルを書き換えず新しい`experiment_id`(EXP-004以降)を発行する）
- 収益指標（PF・純利益等）は本実験の採用/棄却の判断に使用しない

## limitations

- 「候補値と根拠」節の推定発動日数は、決済済みトレードの実現損益のみに基づく試算であり、含み損
  (floating loss)を含む実際の判定とはわずかにずれる可能性がある
- 新規エントリー停止が一度でも発生すると、以降の値動きへの追従経路がEXP-002とは変わるため、
  本試算の「推定発動日数」通りに再現される保証はない
- 本実験はH002の日次損失上限側の機能検証を目的とし、収益性の評価には使用しない
